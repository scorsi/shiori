# Configuration file and format string

## Context and Problem Statement

The author wants a Starship-like experience: a TOML file with a `format` string naming segments, each segment configurable in its own table. The sekkeizu seed used compile-time constants instead. Nim has no TOML parser in its standard library.

Which TOML library, where does the file live, and what exactly is the format grammar?

## Decision Drivers

- Starship-style `format` with `$segment` and `[text](style)` (decided with the author).
- The file is usually generated by home-manager (ADR 0009) but must stay pleasant to hand-write for `keiki preview` iterations.
- Full TOML 1.0: multiline strings are the natural way to write a long `format`.
- Config errors never break the status line.

## Considered Options

TOML library:

1. **`toml_serialization`** (status-im): TOML 1.0 compliant, Nim ≥ 2.0, active (last commit September 2026); pulls `serialization`, `faststreams`, `stew`, `unittest2` into `lock.json`.
2. `parsetoml`: single dependency, but not TOML 1.0 (issue #40 open since years): multiline strings, nested inline tables and mixed arrays fail its own `toml-test` run; last commit January 2025.
3. Own parser for a TOML subset: zero dependencies, but a subset the author has to document and maintain.

Format: Starship-style string (decided) versus an ordered list of segments or JSON (rejected with the author).

## Decision Outcome

**`toml_serialization`** for TOML, decoded into a `TomlValueRef` tree then mapped to the typed config, so unknown keys are reported on stderr rather than rejected.

### File resolution

1. `$KEIKI_CONFIG` if set.
2. `$XDG_CONFIG_HOME/keiki.toml`, else `~/.config/keiki.toml`.
3. Built-in defaults (the `plain` preset, ADR 0006).

Missing file: defaults, silently. Parse error or unknown key: one line on stderr, then defaults for the whole file (partial configs are not attempted, to keep behaviour predictable).

### Top-level keys

```toml
format = """
[$model]($style) $effort $context $fill $rate_limits
$directory $git_branch
"""
palette = "catppuccin-mocha"   # optional, see ADR 0006

[context]
format = "[$symbol$bar $percentage%]($style) [($tokens)](dim)"
bar_width = 10
threshold_warn = 70
threshold_critical = 90
style = "green"
style_warn = "yellow"
style_critical = "red"

[git_branch]
disabled = true

[palettes.catppuccin-mocha]
green = "#a6e3a1"
```

Every segment table accepts `format`, `style`, `disabled`, plus the keys ADR 0005 lists for it.

### Format grammar

- `$name` or `${name}` expands a variable. At top level the variables are segment names; inside a segment's `format` they are that segment's variables (ADR 0005), plus `$style` and `$symbol`.
- `[text](style)` styles `text`; `text` may contain variables and nested groups. A group whose variables all expanded to nothing is dropped entirely, including its literal text (Starship rule).
- `$fill` at top level pads to `COLUMNS` with the `fill.symbol`; at most one per line, extra ones are ignored.
- A newline in `format` starts a new status-line line.
- `\$`, `\[`, `\]`, `\\` escape; anything else is literal.
- A segment referenced in `format` but `disabled`, or with nothing to show, expands to nothing; segments not referenced are never evaluated (ADR 0007).

### Consequences

- Good: a Starship user reads the file without a manual; multiline `format` works.
- Good: dropping empty groups removes the need for per-segment "hide when empty" options.
- Bad: five Nim packages in `lock.json` instead of one; `nim_lk` regenerates it in one command (ADR 0009).
- Bad: all-or-nothing on config errors can surprise; the stderr line and `keiki preview` make the error visible immediately.

### Confirmation

Unit tests for the format parser cover variables, nested groups, empty-group dropping, `$fill`, escapes and newlines (ADR 0008). The example above round-trips through `keiki preview`.

## Pros and Cons of the Options

1. **toml_serialization**: spec-complete and maintained; heavier dependency tree.
2. **parsetoml**: one dependency; no multiline strings and an open compliance issue make it a poor base for a format-string-centric file.
3. **Own subset**: no dependency; a parser to maintain and a subset to explain, for a hobby project that wants to write segments, not parsers.

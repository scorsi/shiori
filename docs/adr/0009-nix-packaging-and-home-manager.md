# Nix packaging and home-manager module

## Context and Problem Statement

Nix is the only distribution channel (ADR 0001). sekkeizu today builds the seed with a plain `mkDerivation` and installs the `statusLine` entry by merging a JSON patch into `~/.claude/settings.json` at activation, because `programs.claude-code.settings` makes that file an immutable store link while Claude Code keeps writing to it.

What does the flake expose, how is the Nim package built with dependencies, and what does the home-manager module own?

## Decision Drivers

- `nix flake check` builds and tests on macOS (nix-darwin) and Linux (NixOS laptop soon).
- sekkeizu imports one module and sets one option; the status line derivation and the `statusLine` patch leave sekkeizu.
- Coexist with `programs.claude-code` without owning `settings.json`.
- Few flake inputs: shiori is a leaf.

## Considered Options

Build: **`buildNimPackage` with `lock.json`** / `mkDerivation` with vendored sources by hand / `nimble` at build time (no network in the sandbox: impossible).

`statusLine` installation: **(a) activation-time jq merge** (sekkeizu's pattern) / (b) `programs.claude-code.settings.statusLine` / (c) require `programs.claude-code.mutableSettings = true` and set the key there.

## Decision Outcome

### Flake

Inputs: `nixpkgs` only. Outputs, for `aarch64-darwin`, `x86_64-darwin`, `x86_64-linux`, `aarch64-linux`:

| Output | Content |
|--------|---------|
| `packages.<system>.shiori`, `default` | `buildNimPackage` with `lockFile = ./lock.json`, `doCheck = true` (ADR 0008); `passthru.presets` points at `presets/` |
| `homeModules.shiori` | the module below (`homeManagerModules` kept as alias) |
| `overlays.default` | adds `shiori` |
| `checks.<system>` | the package (tests included), `nix fmt` check |
| `apps.<system>.{bench,lock}` | `hyperfine` run (ADR 0007); `nim_lk` regenerating `lock.json` |
| `devShells.default` | `nim`, `nim_lk`, `hyperfine`, `nixfmt` |
| `formatter` | `nixfmt-rfc-style` |

`lock.json` is generated by `nim_lk` from `shiori.nimble` and committed; the TOML library and its transitive packages (ADR 0004) are its only entries.

### home-manager module `programs.shiori`

| Option | Type, default | Effect |
|--------|---------------|--------|
| `enable` | bool | installs the package, writes the config |
| `package` | package, `shiori` | |
| `preset` | enum of `presets/*`, `"plain"` | base configuration |
| `settings` | TOML attrs, `{}` | `recursiveUpdate` over the preset (ADR 0006) |
| `configFile` | path, `xdg.configFile."shiori.toml"` | written with `pkgs.formats.toml` |
| `claudeCode.enable` | bool, `true` | installs the `statusLine` entry in Claude Code's `settings.json` |
| `claudeCode.settingsFile` | path, `programs.claude-code.configDir` + `/settings.json` if that module is enabled, else `~/.claude/settings.json` | |

`claudeCode.enable` uses **option (a)**: a `home.activation` entry after `writeBoundary` that creates the file if absent, merges `{"statusLine": {"type": "command", "command": "<store path>/bin/shiori"}}` into it with `jq`, and replaces the file only if the result differs. Declared keys win, everything Claude Code wrote is kept. This is sekkeizu's existing pattern moved here; sekkeizu keeps its own patch for `enabledPlugins` and marketplaces.

Option (b) is rejected because it requires `programs.claude-code.settings` to own the file, which conflicts with Claude Code writing to it and with sekkeizu's patch. Option (c) works but ties shiori to a module the user may not enable (kanna may host Claude Code later) and to its whole-file ownership.

### Consumption in sekkeizu

Input `scorsi-shiori` (git+ssh on Forgejo), `imports = [ inputs.scorsi-shiori.homeModules.shiori ]`, `programs.shiori = { enable = true; preset = "nerd-font"; settings.palette = "catppuccin-mocha"; }`. The `statusline` derivation and the `statusLine` key leave `claude-code.nix`.

### Consequences

- Good: sekkeizu shrinks to one import and three lines; kanna can take them over unchanged.
- Good: the module works with or without `programs.claude-code`.
- Bad: the jq merge runs at every activation and depends on `jq`; a few milliseconds.
- Bad: if Claude Code's `/statusline` command rewrites the key, the next activation reverts it; intended.
- Neutral: `lock.json` must be regenerated when `shiori.nimble` changes; `nix run .#lock` does it.

### Confirmation

`nix flake check` passes on darwin and linux. A home-manager evaluation test in `checks` builds a configuration with `preset = "nerd-font"` and one overridden key and asserts the generated TOML and the activation script contain the expected values.

## Pros and Cons of the Options

- **buildNimPackage + lock**: nixpkgs' supported path, transitive deps handled; one more generated file to commit.
- **Hand-vendored sources**: no `nim_lk`; manual updates of five packages.
- **jq merge (a)**: coexists with every writer of `settings.json`; imperative step at activation.
- **programs.claude-code.settings (b)**: pure Nix; immutable file breaks Claude Code's own writes.
- **mutableSettings (c)**: pure Nix with merge; couples shiori to that module's ownership.
